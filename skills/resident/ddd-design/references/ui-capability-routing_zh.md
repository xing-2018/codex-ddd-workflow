# 能力路由

> 仅供人工审阅，对应[英文执行版](ui-capability-routing.md)，不作为额外执行指导。

按未决设计问题和必要证据路由，不只看工具是否可用。专业能力须可用且满足自身触发与授权规则。用户未明确指定时，可以直接形成合适的最小证据。明确指定能力不可用或受阻时，报告缺口和受影响主张，不能静默换方法或宣称请求的流程通过。改变合同的替代路径交用户决定，同时继续独立且获准的工作。

路由不授权安装、更新、复制、修补或配置专业能力。

| 需要回答的问题 | 可用时优先能力 | 边界 |
| --- | --- | --- |
| 外部事实可能改变设计 | [调研方法](research.md)，包括选定时的Exa | 交接来源、适用性与具体决定，不扩大为泛化发现。 |
| 现有流程需要系统性UX、视觉或可访问性审查 | Product Design audit | 使用截图证据；局部批准修正保留既有视觉基线。audit不批准设计。 |
| 用户要求备选，或存在真实视觉取舍 | Product Design ideation或图像生成 | 只探索争议方向，按提供方当前brief／选择规则执行；构建前取得所需选择。 |
| 交互或状态转换必须运行才可判断 | [实验方法](experiments.md) | 验证有界行为，保留已批准视觉方向。 |
| 选定视觉目标需要可操作前端原型 | 可用原型能力，包括满足触发条件的image-to-code | 绑定准确选定来源，选择Product Design时使用[交接方法](product-design-handoff.md)。按预览合同交付独立HTML，创作或开发预览本身不足。保留内存状态及预设结果，无业务I/O或计算。 |
| 本地Web或Electron需要功能、响应式或视觉验证 | `playwright-interactive` | 遵守控制授权；QA证据不建立设计权威。 |
| 用户明确选择外部设计环境 | 可用设计能力 | 遵守提供方与授权规则，将渲染证据返回当前对话。 |
| 专业能力不能实质改善结果 | 直接使用ddd-design | 构建并验证最小忠实预览。 |

按产物和动作判断能力，不看名字是否包含code。UI设计可以在既有预览授权内构建安全、可恢复的前端原型。业务实现、真实文件／服务／持久化集成或计算交回ddd-flow；其获准也不会将它纳入UI原型。外部发布和部署保留相应审批。遵守实际触发、视觉源和工具限制；不强制直接UI设计依赖插件或固定备选数量，不同时使用多个专业能力寻求重复保证。

完整体验原型归ddd-design。只有确需运行的有界疑问才使用实验方法，并非所有可点击页面都需独立逻辑实验。能力输出只是证据，不能批准领域或UI设计变化。

选择Product Design路径后，在依赖写入或验证前读取[交接适配](product-design-handoff.md)。它绑定实际宿主、权威、路径、QA和导出证据，不替换提供方当前流程。没有视觉目标时按其选择方法处理，不编造构建目标；已选定的局部修正不重启整产品ideation。

每个路由问题只保留准确问题、证据、答案与限制，以及它改变或确认的设计决定。
