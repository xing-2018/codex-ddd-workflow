# UI design within the change contract

Read for UI creation, modification or review, including work on a settled approved interface. Apply the defaults below without restarting design or approval for unchanged decisions. `ddd-design` owns the connected requirements, technical design and UI direction; UI evidence cannot create domain semantics or implementation permission. Use the same representative scenario, input meaning, state transitions and expected result in the brief, design, prototype and verification record.

## Establish the design question

Inspect the affected requirements, approved design, current product and target platform. Identify the user role, task entry and end, representative inputs and results, existing layout and controls to preserve, changed region, default window size, important error or cancellation state, and the one material question this preview must answer. If the requirement itself changes, return to G1. A defect within an approved direction can be corrected without reopening the product goal. Mark unevidenced sizes or visual choices as candidates.

For an explicitly authorized local change, recover the latest approved baseline and preserve its surrounding labels, notices, navigation, controls and layout; unapproved additions in the current product are not preservation requirements. A format conversion does not authorize dropping cases, choices or interaction states. Reuse the product's vocabulary and visual language. Resolve reversible styling within the approved direction and execution scope; ask for a new material choice when it changes the action path, hierarchy, accessibility, persistence or scope. Unclear execution permission still returns to the user before writes.

## Stable layout and task-focused content

Apply these defaults unless the approved design or an explicit user decision requires different behavior. Preserve necessary safety, security, accessibility and task information; minimal presentation is not permission to conceal it. Restore an approved baseline rather than preserving unapproved additions found in current code.

- **Keep the change local.** Preserve the approved theme, product-window dimensions, region sizes, control order, navigation and information density around the changed behavior. Do not redesign a whole page or add columns, controls or explanatory cards to complete a local fix. For a new interface, design one stable structure across its representative states.
- **Keep state changes within their regions.** At the same viewport, no-data, loading, empty-result, error and temporarily unavailable states should retain the surrounding controls and content regions. Prefer visible disabled controls for temporary unavailability over removing them and shifting their neighbors; retain approved permission-based or conditional visibility. Use the existing content or feedback region for concise state information. Do not replace an empty chart or table with an unrelated introduction that resizes the page. Intentional responsive reflow, text scaling and an approved expand/collapse interaction remain supported.
- **Use clear entry controls.** Settings, details and help open through an explicit button or the approved navigation. Reuse the existing page or dialog pattern for editing; do not introduce an inline expansion that pushes the working surface aside merely to avoid a separate entry. Keep prototype review controls distinct from product navigation. Do not add a help icon to every field by default.
- **Make interface copy earn its space.** Include text that identifies a task, input requirement, action, result or necessary risk. Prefer a clear label or control over instructions that repeat it. Do not add design-change commentary, implementation details, feature advertisements or permanent explanation banners to the product surface. Put authoring and review notes in the accompanying design or prototype documentation; the preview contract owns simulation disclosure.
- **Keep useful feedback visible and accessible.** Preserve errors, progress, validation and action outcomes using an appropriate existing feedback surface and target-platform accessibility semantics. Do not hide required information in hover-only tips or external documentation, announce every ordinary update, steal focus for routine feedback, or replace every message with a toast. Optional contextual help may use an existing accessible disclosure or help entry when a real user need warrants it.
- **Verify the transitions, not only the populated screen.** Compare the approved and changed interface at the same product dimensions in affected normal, no-data, loading, disabled and failure states. Check surrounding positions, retained controls and navigation/draft state, and operate necessary feedback and help. A screenshot only certifies its captured state; a low browser layout-shift score does not prove that user-triggered transitions preserve the approved layout. Report unavailable evidence and return a required material layout change to its design owner before dependent implementation.

## Connect four representations

- The written design states the action's conditions, result, prohibited behavior and failure or cancellation outcome. Its user reading area comes before implementation fields.
- A flow, state or sequence diagram explains a genuinely complex relationship; use the applicable [Mermaid method](../../chinese-docs/references/mermaid.md) directly. The text remains the authority for a decision the user must approve.
- An operable prototype exposes the representative task and material states. Read the [preview contract](preview-contract.md) before creating or converting it; a static rendering suffices only for a settled, local visual question.
- The record identifies the path actually operated, observations, simulation and unverified behavior. A screenshot, source file or successful build alone does not prove the interaction.

For a workflow prototype, deliver directly openable offline HTML with representative embedded data and in-memory interface state. Open, save, export and calculate controls demonstrate selection, confirmation, feedback and results without real file access, downloads, browser persistence, services or domain computation. Keep the existing selectable cases and relationships; use predefined outcomes consistent with the known scenario. Native focus, widgets, device behavior and real computation need separate evidence when material.

## Iterate and approve

When the user gives local feedback, state what was observed, the proposed region or behavior to change, preserved decisions, affected design clause and the path to recheck. Apply the router's execution authorization before changing the affected contract or prototype states; feedback alone is not permission to write. Stay within valid authorization and do not rebuild the whole screen without a changed task path or evidence. When a core path repeatedly fails review, stop stacking unrelated adjustments: recover the approved reference, revisit the scenario and success condition, and verify a representative complete path before expanding again. Keep fixed entity/geometry identities and approved visual choices unless the requested delta changes them. If a material choice requires hands-on judgment, obtain preview-write authorization for one complete representative path before broadening variants; formative feedback does not approve the final design.

For G2, identify the brief, design, prototype entry and every local resource the entry depends on, plus representative cases, visible states and simulation limits. An approval of `index.html` alone does not cover changed styles or scripts. After approval, compare production implementation against the same scenario, data, state and target dimensions. Treat unexplained differences in hierarchy, interaction or data relationship as design fidelity gaps; do not require pixel identity for platform font rendering.

If routing a bounded visual or technical question to a specialist would materially help, read [UI capability routing](ui-capability-routing.md). A specialist returns evidence, not approval. Present the usable artifact and the precise material direction for user review; retain an authorized reviewed reference and an opening path. If rendering or operation cannot be verified under current tool permissions, report that gap without marking visual acceptance complete.
