# Product Design handoff

Read only after Product Design is selected for the current question, before dependent writes or verification. This adapter connects its current workflow to [DDD's preview contract](preview-contract.md); it does not invoke, install, copy or override the provider. The [Chinese review copy](product-design-handoff_zh.md) is for human review only.

## Bind the task before creation

Recover the approved task, scope, current layout/states and exact selected visual source at a revision or recoverable content identity. Use the provider's focused entry for audit, ideation or implementation as applicable; a local correction preserves its selected target, while a new direction follows the current brief and user-selection rules before build work. Do not copy a provider's candidate count into every DDD task.

Identify the actual host and callable capabilities under the provider's current instructions. Desktop and cloud Work preview/browser conventions differ; do not hard-code another host's URLs or APIs here. Respect tool restrictions and project authorization, including explicit computer-use activation. Missing capture, QA, viewing or export capability leaves its claim unverified; it does not authorize installation, account/configuration changes, a new conversation or broader permissions. Do not silently replace an explicitly requested provider. A fallback that changes its contract needs a user decision.

Before files or processes, include the covered write/launch/check actions and resolved paths in the existing preview plan: project root, authoring/runtime root, dependencies and build outputs, the provider's required QA file, task evidence and final entry/resources. Reuse the existing `.planning` owner and approval; do not introduce another approval or research store. Capture permitted evidence only in the project's task evidence location. A provider-required QA file remains at its required root, with its role and pointer recorded; do not relocate it and claim provider completion.

`docs/design/prototypes/src/` is a possible authoring root, not a certified provider project root. Check the current provider/tool contract and demonstrate compatibility when actual execution is authorized. It may have a source `index.html`, but that is authoring input, not another maintained review entry. The sole final review entry stays `docs/design/prototypes/index.html`, with the required README and design owner/pointer. If required paths or dependencies conflict with the approved boundary, resolve that exact conflict before writes; do not create a parallel prototype or silently drop required QA.

## Preserve design through export

Keep the selected source, representative paths, relevant states, data meaning and approved layout throughout provider build, QA and export. Apply [conversion and fidelity repair](preview-contract.md#conversion-and-fidelity-repair) to the actual exported artifact. Keep business operations simulated through in-memory state and predefined outcomes; do not introduce real files, persistence, services or computation merely because the provider outputs runnable code.

Provider authoring, development preview and required QA are intermediate work. Export the independent HTML entry and packaged resources under the existing contract; no authoring checkout, dependency installation, build step, backend, CDN or network request may be needed for its agreed path. Observe actual final paths, dependencies and sidecars. A running development page or successful build cannot certify this export.

Preserve meaningful engineering charts, geometry, accessibility and review targets. If the provider's asset rules cannot preserve a semantic visualization, narrow its visual responsibility or obtain a scope/method decision; do not flatten an operable engineering view into a decorative bitmap and claim equivalent functionality. Use original assets when appropriate under the selected provider's actual rules.

## Hand off distinct evidence

Use the existing task/design evidence owner, with the reviewed source and final artifact identities and exact exercised scope. Distinguish these conclusions:

| Claim | Required evidence |
| --- | --- |
| Visual and interaction fidelity | Actual source and current implementation opened and compared at matching viewport/state, with applicable core paths exercised. |
| Provider build QA | Its required report at its required root, actual comparison, blocking repairs and recapture/recheck under the current provider rules. |
| Final offline prototype | The exported entry directly opened offline without product/preview services; in-scope paths exercised and handlers inspected under the preview contract. |
| Native annotation support | Actual target selection, comment submission and return in the intended host, with the contract's required content/state coverage. |
| User design acceptance | The user's authentic approval of the identified artifact and scope, separate from all technical verdicts. |

Do not write a PASS field to stand in for observation or reuse one row as another row's evidence. If capture, comparison or required QA is blocked, retain the provider's blocked result; an iteration limit cannot override blocking issues. Stop nonblocking polish under its actual method rather than looping without a decision. Source maintenance or a read-only adaptation review can finish within its authorized scope while provider runtime, offline or annotation evidence stays explicitly unverified. Do not present an unverified prototype as completed provider handoff or accepted design. Return to ddd-design for the real design decision and to ddd-flow for separately authorized implementation or delivery.
