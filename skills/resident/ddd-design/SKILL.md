# DDD Design

Own one connected design for the requested change: what the user needs, how the system and interface satisfy it, and the next implementable slice. Choose only the branches the unresolved question needs. A UI prototype, technical experiment, diagram, code or test is evidence; none grants approval or changes the product contract by itself.

When selected by `ddd-flow`, reuse its Authority Baseline, Change Envelope and Persistent Write Boundary. Direct invocation first reads [ddd-flow](../ddd-flow/SKILL.md) for those guards and its continuation rule. Apply its [design approval](../ddd-flow/references/design-approval.md); reuse settled G1 or G2 decisions and obtain approval only for new material semantics. This Skill adds no per-file gate. **Requirements-only** work describes what and why, constraints and acceptance; it does not select architecture or implement product code.

Start read-only and present the detailed change or preview plan in the conversation. Desired results and feedback do not alone authorize writing designs, records, prototypes or temporary evidence. Before those writes, identify explicit execution authorization or valid bounded autonomy under the router's approval reference. Unclear meaning or permission returns to the user before dependent changes; available tools and reversible artifacts do not settle it.

## Connect the change

1. Recover applicable requirements, current product, designs, glossary, ADRs, configuration and callers. Separate approved facts, observed behavior, proposed change and unknowns. Investigate discoverable facts before asking. For design-document review or drafting, first read [design document authority](references/design-documents.md) and recover the complete applicable writing contract, including earlier corrections; later feedback changes only the affected clauses. Reuse valid guidance and existing owners rather than creating another tracker. Use the router's unified `.planning` entry and migration method; read-only design work reports record gaps without creating files.
2. Use [requirements](references/requirements.md) to state the user task, representative normal and failure scenarios, scope, exclusions and observable acceptance. Map each material requirement to the answer it needs; do not copy its text into every artifact.
3. Design the relevant transformation or algorithm, input meaning and units, state owner, interface, ordering, failure, recovery and resource constraints. Use the same scenario across these views. Equivalent private implementation details remain with implementation; changed outputs, defaults, persistence, timing or dependencies require design approval.
4. For UI creation or modification, including an approved existing interface, read [UI design](references/ui-design.md) and apply its stable-layout and task-focused-content defaults; settled design does not require another approval gate. Read its [preview contract](references/preview-contract.md) before building, modifying or verifying a prototype, including its single-project layout, migration, [capability-based viewing route](references/preview-contract.md#scope-routing-and-viewing-tools) and [native browser review and annotation coverage](references/preview-contract.md#native-browser-review-and-annotations). UI design and technical design share one scenario and one design owner. Complete multi-page previews share navigation and in-memory state; the contract permits safe authoring-time presentation reuse while keeping the built artifact independent. Return contradictions to the fact owner rather than letting the prototype invent computation or data semantics.
5. Read [domain](references/domain.md) for ambiguous durable language or an ADR decision; [architecture](references/architecture.md) for a real boundary or seam and [stack adaptation](references/stack-adaptation.md) only for unresolved runtime, project-shape or process-boundary choices; [research](references/research.md) for an outside fact that can change a decision; and [experiments](references/experiments.md) for one bounded runnable uncertainty. These are conditional methods, not a fixed sequence. Use the requirements method's interview branch only when the user asks to stress-test a decision.
6. Present one reviewable design with a user reading area first: goal, operation, changed and preserved behavior, reason, error or cancellation, prototype or sample path, and the exact decision awaiting approval. Follow with implementation responsibilities, data and state, interfaces, failures, verification and migration only where applicable. Check concrete user steps against applicable project behavior and approved design; code identifies current implementation and gaps without removing approved targets. The active change's `brief.md` and `design.md` hold new requirements and design, or point to existing owners without duplicating facts. Design document authority governs long-lived facts and their content boundary. Persist only within the router's write boundary; document delivery defaults to Markdown.
7. When implementation planning is requested or needed for an approved design, read [planning](references/planning.md). Identify the current vertical slice, expected result and checks. A single slice belongs in `record.md`; a separate plan is for real multiple-slice dependencies. Design approval does not approve implementation, and planning does not execute the slice.

## Completion

Before delivering a design document, compare its actual paragraphs and scenarios with the complete writing contract using [Chinese Docs' content review](../chinese-docs/references/review.md). Correct in-scope deviations within existing authorization; report unresolved semantic choices. Links, formatting, counts and hashes establish only their own checks, not content conformity.

When updating a prototype or design record, apply only [ddd-flow's State vocabulary](../ddd-flow/references/recovery.md#state-vocabulary) and the applicable structural check before signoff. Do not invent a status from human-facing wording; an operable preview pass does not validate its record or grant G2/G4 approval.

Requirements-only work ends with a testable what-and-why draft or approved baseline and explicit unresolved choices. Combined design is ready when material requirements have implementable answers; algorithm, data and UI views agree on shared scenarios; failure and acceptance are clear; and new material choices are approved. Identify the approved baseline, actual prototype entry and dependent resources, verification evidence, unverified limits and next gate. Return to `ddd-flow` for authorized continuation rather than treating a completed document or preview as a product implementation.
