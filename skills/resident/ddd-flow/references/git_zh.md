# Git规则：中文审阅版

> 对应[英文执行版](git.md)，仅供人工审阅，不作为额外执行指令加载。

项目写入或Git操作前读取，包括机械编辑；读取本参考本身不启用DDD。

使用工作树须有本次会话仍有效的明确授权。提交或推送请求不授权创建、切换本地分支或创建远端分支。

首次向用户指定的非Git根目录写入需要版本管理的交付物前，除非用户禁止，否则初始化Git。不得创建嵌套仓库；基线提交前排除敏感文件、生成产物和大文件。

对于需要版本管理的交付物，必需审阅和检查通过后，只在本地提交本任务内容，不留下本任务未提交的改动。完整保留其他任务的内容和暂存状态；工作树有其他改动时无须清空。发现无法隔离的改动时报告，不能纳入或丢弃无关内容。只读任务不创建提交。已知存在并发Git活动时，按[共享检出协调](execution.md#shared-checkout-coordination)协调完整的暂存、审阅和提交过程；保留其他任务的暂存及锁，无法隔离的依赖须报告，不混合候选。使用Conventional Commit类型和简体中文提交信息。

## 仅运行操作的任务

仅处理运行数据、缓存或进程，且没有需要版本管理的交付物时，不为满足流程初始化Git、新建受Git跟踪的工作流记录或创建提交。必要且获准的证据放入项目指定的Git忽略位置。用户或项目明确要求归档或提交时，以该要求为准。本例外不授予操作权限；源码、正式文档和配置变更继续遵循原有交付规则。

## 整合已有成果

获准整合PR或同步main时，应用前固定来源修订、目标基线及既有工作区／暂存内容。能够恢复批准行为和执行授权时，沿现有实施路径处理；整合请求不代替缺失的设计批准。范围内等价接线自主处理，只有实质行为、数据或接口冲突交回设计。保留必要依赖和无关工作；本地优先不授权丢弃引入内容，也不代表全部冲突使用`ours`。

区分本地整合、远端发布、另一主机源码同步、数据库迁移、服务重启及实际UI／数据操作。从既有权威恢复各项请求的授权和项目前提，使用当前记录或对话，不新增矩阵或台账。共享目录有未提交改动时，阻塞受影响写入或同步；只有已识别的项目依赖才使其他动作受阻。保留必需跨主机门禁，延后前取得真实例外批准，复用范围内仍有效的延后决定；不据此获得联系或接管其他任务的权限。

创建整合提交前识别项目必需检查。能够检查固定候选的检查，在更改目标或创建提交前完成，包括适用的空白、清单、链接、版本及拟用提交说明；只运行获准检查，并保留依赖实际整合的必需检查。只有具体冲突或验证需要才在获准位置使用隔离副本，不为方法本身创建分支或工作树。应用前重查来源及目标漂移；来源更新只使受影响证据失效，必需最终集成和发布检查仍保留。

## 按声明选择内容身份

Git源码候选按路径、文件模式以及项目实际attributes和clean转换后的blob身份比较。检出或归档可能含转换后的换行；原始字节不同不单独证明源码漂移。依据实际Git规则解释差异，不能任意归一化空白，无法解释的差异继续保留。该比较不授权改写工作内容。

保留用户既有改动可能需要原始字节及暂存内容；交付物字节检查使用实际清单和哈希，两者都不能以源码规范化等价替代。行为、正式源码验收和安装仍使用各自证据合同；Git树一致不证明这些结论。

## 提交组织

既有工作区或暂存改动涉及本任务时，在实质编辑前判断边界。比较HEAD、可恢复的任务开始时工作区内容和当前内容，区分本次修改、必要依赖及无关工作；单独保留原暂存状态。复用已有证据，来源不明时报告，不编造归属。已批准范围内的安全隔离及仓库授权提交自行完成，不让用户选择文件。必要依赖超出范围或不能安全隔离时，先说明最小未覆盖内容、必要原因及受阻动作，补齐缺失授权后才扩大候选；不得静默纳入既有工作，也不能仅因交叠就视为任务完成。

一个任务可以包含多个提交。暂存前，按具体修改目的组织能够连贯审阅、验证和回退的变化。修复或能力与必要调用方、测试、文档和版本变化一起提交。可独立成立的设计更新、工具、工作流和清理分别组织；同属一个任务、目录或交付期限不足以合并。不要按文件数量、目录或固定提交数拆分。拟定顺序须保留有效依赖；紧密耦合的修改可以放在一个提交中。

不主动引入无关格式整理。受影响内容中必要且不改变语义的空白或文件末尾换行修正，应在创建相关实现或整合提交前完成并随之交付，不属于可独立成立的清理。提交后才发现时，保留历史，先确认必需检查是否实际阻断交付，不自动amend、rebase或追加纯美化提交。硬门禁只能通过单独修正或历史修复满足时，先提出这项最小例外并取得适用决定；不能为避免独立提交而夹带无关内容。

每个拟提交说明目的、文件或修改段落范围、必要依赖、适用验证和拟用说明。使用现有对话或任务记录，不新增强制台账。共享文件可能需要按段落拆分；保护无关内容和暂存。无法隔离时报告依赖，不能扩大候选或丢弃修改。

每次提交前，读取完整暂存差异，对照上述边界、批准范围和提交说明。在现有授权内先修正缺乏必要关联的混装或不准确描述，再提交；技术检查和记录中的PASS不能代替这项语义审查。审阅交接或推送时，检查准确候选范围中的每个提交，不能只看合并后的最终Git树。内容未变时复用仍有效的审阅和验证；暂存候选变化后，只重查受影响证据。

仓库浏览器中多个目录重复显示同一标题，以及文件数量多，本身不构成失败。按整个提交的目的和依赖判断；部分路径只改README，不会使包含必要代码修复的提交变成纯文档提交。质量发现不授权改写已发布历史。后续流程修正与明确请求的历史修复分别处理；后者须有独立批准和恢复方案。

## 提交信息

创建任何提交前，从项目指令和已有检查器恢复允许类型、语言及必需说明检查。冻结前将这些规则用于拟用说明；通用语法通过不代表项目合规。项目检查器只接受既有提交时，创建前先核对适用规则，创建后仍运行必需范围检查。不修改检查器、启用钩子或另造政策来让说明通过。

在项目规则内按实际变化选择类型：新增能力用`feat`，修正问题用`fix`，仅文档变化用`docs`；其他变化使用项目允许且适合的Conventional Commit类型。发布动作或版本递增不决定类型。版本影响仍按项目版本规则独立判断。

标题说明具体变化及结果，读者无需打开差异就能知道新增或修正了什么。版本号可作为补充；“发布版本”“优化内容”等笼统标题不足以描述变化。原因、使用影响或重要限制需要解释时补充正文，简单改动不强制长正文。

提交前，将类型、标题及正文与完整暂存差异和批准范围对照。确认描述符合实际变化和证据，排除个人信息、私有来源、本机路径和凭据。自动生成的提交信息也须同样审阅，不能替换成固定的发布标题。这些检查不授予提交、推送或改写历史的权限。

## 冻结说明与核对交付

普通提交前，冻结实际已审阅的说明和暂存内容。使用本Skill的[git_delivery.py](../scripts/git_delivery.py)、项目获准Python和任务产物位置。freeze将说明复制为UTF-8／LF并保留末尾换行，绑定说明字节、仓库、HEAD及完整暂存清单；有冲突条目或输出目录已存在时拒绝。人工核对产出的message.txt是否为简体中文、符合实际范围且无敏感信息。提交必须消费同一文件：`git commit --cleanup=verbatim -F <freeze-dir>/message.txt`，不能检查后临时重写-m。收据只记录输入身份，不构成授权。

提交后，对该收据及实际提交运行verify-commit，核对原始说明字节、预期父提交和完整提交条目是否匹配冻结值。说明、暂存内容、父提交或检查器变化使对应证据失效：停止依赖交付，查明原因，仅补真实缺失授权；不能自动amend或改写历史，保留失败尝试。源码、版本、链接或空白检查通过不证明提交说明合规。

获准推送前，观察真实目标分支尖端、固定候选HEAD，用check-range检查该准确范围中的**每个**提交，并完成原有差异／说明语义审查。目标须仍符合已观察状态，实际候选须匹配受检HEAD；漂移后重新检查范围，必要时取得新决定。中间提交标题无效时，即使最后一条合规也须失败。此检查不推送，不授予发布权限。

调用参数与英文执行版相同：freeze使用--repo、--message、--output；verify-commit使用--repo、--receipt、--commit；check-range使用--repo、--base、--head。目录和固定身份必须取实际值。

脚本检查Conventional主题格式并拦截摘要没有中文字符的情况，只有scope含中文不算通过。它不能认证简体中文用法、语义质量、声明真实性、内容安全或授权；不安装钩子、不改配置、不创建提交、不访问网络、不推送。提交核对入口适用于已有仓库的普通单父提交。首次／合并／amend、明确不同语言合同或工具不可用时，按实际规则保留等价的精确说明、父提交／内容和完整范围证据；不能收窄原有支持，也不能仅通过不用工具来省略检查。收据只放获准任务位置，不新增强制项目台账。
