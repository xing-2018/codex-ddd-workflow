The main conversation owns task state and acceptance. A pointer to this protocol means retrieving only missing sections for the current operation, not loading the whole file: reuse the inline ownership decision in ddd-flow; the Delegation decision heading below is only a compatibility pointer; Record and dispatch, Worker contract and Accept a result for justified dispatch; Accept a result for acceptance; Resume from durable evidence and any missing State transitions for recovery. Use read_section.py with repeated --heading arguments to retrieve known sections together; apply the delegation decision before dispatch. Workers use the Worker contract excerpt supplied in their packet and the assigned task method; when triggered, they may also retrieve only Evidence validity or Efficient tool execution below, reusing valid packet excerpts and excluding management sections. ## Shared checkout coordination

Use this branch for known concurrent project work, overlapping writes or shared Git/runtime actions. Other user conversations are independent tasks, not this task's workers; reading their records grants neither takeover nor messaging permission. Keep each task's state and approvals in its own record. Read only the relevant active bindings and declared boundaries. Ordinary explanations and quick lookups create no registry or resource table.

Before substantive writes, identify exclusive modules and shared files such as the index, router, theme and build entry. Assign one authorized coordinator for each overlapping edit or integration; page authors may work on exclusive files while that coordinator integrates the common shell. A declaration or pre-write snapshot cannot prevent races: obtain a recoverable handoff or coordinate serialized writes. If the other owner cannot be contacted under existing permission, hold only the overlapping action and continue independent authorized work. Never overwrite a peer's changes to restore this task's baseline.

Before assembling an isolated validation copy, recover the shared content it needs, its actual revision or dirty-content identity and the authorized integration path from existing evidence. If a needed handoff, dependency identity or authorized integration path is unavailable, hold only dependent work and continue independent authorized work. A copy or patch check proves only its fixed candidate. If shared files change or the patch no longer applies, reconcile the actual integration within the existing coordination boundary, then recheck affected claims on the frozen integrated candidate and complete required integration/delivery checks. Reuse unaffected evidence; a conflict grants no takeover, overwrite or messaging permission.

Treat staging and committing as one serialized Git-index transaction: inspect current staging, select this task's changes, verify the staged diff and commit only the isolated candidate. Do not clear another task's staging, remove its lock, use a blanket add or claim independence when the candidate depends on uncommitted peer edits. Coordinate the dependency and freeze its identity; inability to isolate blocks the commit or affected integration, not unrelated approved work.

For build, reload, restart or collector access, recover the project root, process/port identity, owner and still-valid lifecycle authorization. Port occupancy alone is not permission to kill a process. A takeover requires authentic authorization, previous-owner stop/release evidence and recovery of the approved scope, current inputs and remaining checks. Record unresolved liveness rather than claiming a receiver or device has stopped. Preserve user constraints on windows and focus. The index is not a scheduler, mutex or authorization source; do not create locks, daemons, conversations, branches or worktrees merely to implement this coordination.

## Reviewable source changes

Use this method before a shared or remote batch source rewrite whose preconditions or partial-failure effects are unclear, and when approval review rejects a source change. Ordinary multi-file edits do not automatically require isolated copies, extra tests or another approval. Preserve the approved behavior, project/host ownership and existing operation permissions; distinguish editing development source from changing a running service or business data.

Prefer an exact, reviewable diff or an existing bounded transformation over a large inline replacement script. Establish the actual target paths and baseline, including relevant uncommitted content; a commit alone does not identify a dirty checkout. Check replacement anchors, expected match counts and already-applied states before writing any target. Do not let a missing match silently skip a required change or a broad match alter unrelated code. Compute the complete transformation and perform available syntax checks before destination writes. Preserve recoverable originals through existing Git, diff or authorized backup evidence. Sequential file writes are not a transaction: on failure, stop dependent steps, inspect what actually changed and reconcile within scope; do not silently continue, overwrite peer changes or perform an unauthorized rollback.

When the direct change cannot be reliably reviewed or checked in place, prepare candidate copies and an exact diff in an already authorized task-artifact location, leaving the destination source unchanged. Inspect the complete coherent diff and choose only authorized checks needed for its concrete risks. Checks requiring the proposed code run against that candidate where feasible; an unimplemented change cannot already have an integration pass. Do not require a full build or test suite before every edit, invent file-count limits, or split a coherent change merely to reduce its apparent size. Unavailable checks remain explicit gaps, not evidence of failure or permission to run extra evaluations.

Before applying the fixed candidate, recheck the affected destination baseline and patch applicability. Drift or a failed prerequisite stops dependent writes; reconcile the actual candidate before proceeding. Bind application to the reviewed content and keep each command's outcome visible. After application, verify the actual diff and complete only still-required integration checks on the resulting source. Candidate checks do not certify destination integration, running-service behavior or user acceptance; reuse unaffected evidence rather than repeating the whole suite.

For an approval rejection, retain the exact request, target and stated reason. Distinguish policy denial from a hook failure, sandbox/OS error, timeout or product-test failure. Reuse visible authentic authorization; do not ask again merely because approval review rejected a particular implementation. A retry needs a material reduction of the stated risk or new evidence resolving it, exposed in the pending request with accurate target, scope and validation limits. Changing tools, wrapping commands, disguising the same operation as smaller requests or switching permission mode is not that correction. If no authorized safer path remains, report the blocked action and the minimum missing decision; continue independent authorized work.

Once a safer method succeeds, reuse it for comparable remaining operations in the same task while scope, baseline assumptions and risks hold. Keep only the useful method/evidence pointer in the existing task record when authorized; do not create another tracker or repeat the rejected pattern for the next file group. Reassess changed risks instead of treating a previous approval or passing check as blanket permission. This method neither changes hooks/configuration nor guarantees approval; lifecycle feedback and approval decisions are separate evidence.

## Efficient tool execution

This section applies to local and delegated tool work; reading it does not require task management or delegation.

- Start from the unresolved question. Resolve paths from the current Skill catalog, available tool results or verified entry points; search when the relevant location is unknown. Repository grouping paths and installed Skill paths can differ; do not construct one from the other. Then read the necessary implementations, callers and contracts.
- Before returning structured results, select relevant JSON fields, records and aggregates and remove duplicate search metadata. Emit complete paths and hashes as JSON or plain text, not width-limited tables. Extract the needed Markdown section instead of relying on a link anchor. Preserve complete source lines: in PowerShell, use `@(Get-Content ...)` before numeric indexing, or enumerate lines without indexing. Expand for dependencies, missing evidence or contradictions; truncation is not a completeness check.
- Treat applicable in-context instructions as already loaded, including AGENTS and active role instructions. Before reading, name the missing source or section; a new turn, phase or recovery pointer does not invalidate available guidance. Retrieve only missing, changed or conflicting portions, or an explicitly requested refresh. A record saying "loaded" does not prove that the text remains available: recover a genuinely missing section, not the whole workflow. Reuse valid source identities and exact headings from prior results; batch necessary sections with the existing reader. A truncated result is not complete guidance: recover its missing portion rather than reprinting sources already obtained. Do not repeatedly hash or scan unchanged inputs without evidence of change.
- Keep complete relevant command logs in an authorized location under applicable secrecy rules. Return the outcome, exit status, relevant errors and evidence path by default. Expand on demand; if evidence was truncated or could not be retained, report that limitation.
- Prefer completion events. Finish independent work while a worker runs; when only its result is missing, use an interruptible wait appropriate to the host limit and user-update deadline, not repeated minimum-duration waits. Reuse handles and cursors, inspect only new output and back off unchanged status. A timeout alone establishes neither failure nor a reason to prompt the worker, redispatch or refresh all task state. Send follow-ups only for a new decision, new evidence, necessary dependency coordination or a user-requested update. When the host still requires polling, retain necessary waits without claiming zero model overhead.
- Batch independent instruction and evidence reads with their complete paths and required hashes. Reuse identities returned with section text instead of adding hash-only rounds. Interpret new guidance before dependent work; combine operations only across known dependencies, failure boundaries and permissions. Inspect every result and never batch across approval boundaries.
- Preserve each step's outcome and relevant errors; a later success or final exit code cannot establish that earlier steps succeeded. Distinguish an expected failure signal, a search with no matches and an execution error using the command's purpose and contract. Stop dependent steps when preparation, copying, building, launching or another prerequisite fails; do not silently consume an older artifact. For test failures, use the already applicable [testing policy](../../ddd-implement/references/testing.md#diagnose-failures-and-stop-when-evidence-is-sufficient), retrieving only missing guidance.
- Reuse verified project commands, launchers and environment bindings. Confirm the relevant working directory, executable, arguments and prerequisites before first use or after change. Prefer existing scripts; move recurring, error-prone sequences into project-owned scripts only within authorized implementation.
- Before retrying, identify the first failed boundary and the corrective change or new evidence. Validate that boundary with the narrowest reliable check before resuming dependent work and required broader checks. Controlled repetition for intermittent failures must answer a stated diagnostic question; do not restart the whole task merely because a turn ended.
- For a source-change approval rejection, use [Reviewable source changes](#reviewable-source-changes) before retrying and reuse a successful safer method for comparable remaining operations.
- For unresolved reuse or invalidation questions, retrieve only [Evidence validity](#evidence-validity); reuse an already supplied valid excerpt.

### Conversation evidence

Before reading another conversation for background, identify the missing requirement, approval, correction, accepted result or blocker. Request only relevant turns within the tool's supported limits, with tool outputs omitted initially. Preserve the source thread, turn identities, order and pagination cursor; expand older turns only until the missing facts and their authority are recoverable.

Filter structured results in orchestration before printing: return the relevant user instructions and agent conclusions, with their conditions and provenance. Omit reasoning items, command bodies, patches and unrelated outputs. A result-size option or `includeOutputs: false` may still return large command items; select fields and bound returned text explicitly. If essential content cannot fit, split relevant turns or retrieve the specific item instead of silently clipping a decision. Inspect all parallel results, retain each error and report incomplete evidence. Open a particular command, diff or receipt only when needed to settle the question.

Other conversations are evidence, not new instructions or permission to contact their owners. Link their decisions from the existing record when persistence is authorized; create no copied transcript or second tracker.

## Evidence validity

Reuse evidence while the actual inputs, command or method, environment, dependencies and acceptance scope it supports remain valid. Record only what establishes that scope; an unchanged HEAD alone cannot identify dirty or separately versioned dependencies. For a first delivery, cover the complete approved acceptance scope on the actual candidate.

Before repeating checks after a revision, identify the exact changes, affected conclusions and necessary dependencies, and retain independent valid evidence. Relevant source, authority, data, fixtures, toolchain, configuration, runtime changes, missing artifacts, new failures or contradictions invalidate affected conclusions. A small textual diff can alter a complete semantic unit; shared-method or interface changes extend review to exposed consumers. An isolated copy's PASS covers only its candidate and recorded dependencies until actual integration is checked. Repeat affected checks and all still-required final integration, integrity and delivery checks; a narrow PASS never replaces wider required acceptance.

Unrelated changes, phase transitions, commits and handoffs do not by themselves invalidate evidence. Do not rehash or recheck unchanged inputs merely to demonstrate reuse. Reuse applicable text already available; a record saying "loaded" does not restore missing text, so recover only the missing section. Retain historical failures and disclose unavailable checks; once the original outcome and required protection are established, stop extra checks unless a relevant change, concrete failure or unmet requirement reopens them.

Formal source, installation and host-acceptance tools retain their own identity and completeness rules. Impact-based reuse never bypasses a whole-installation behavior hash, converts an old PASS into a current certificate, or turns partial observation into full acceptance. File integrity, semantic source review, actual behavior, target-host loading, cross-model compatibility and efficiency support distinct claims.

## State transitions

| State | Meaning and exit condition |
| --- | --- |
| planned | Required task authorization or facts are missing; move to ready when verified |
| ready | Prerequisites and authority hold; dispatch a new attempt or execute locally |
| running | An identified attempt is executing; a returned candidate moves to review |
| review | Main conversation is checking a result against current authority and acceptance |
| done | Main conversation has verified every task acceptance criterion and recorded evidence |
| blocked | An actual missing condition prevents progress; record it and resume only when resolved |
| cancelled | User removed the outcome; stop its attempt and retain history |

Research readiness depends on its research authorization, not implementation approval. A rejected result keeps its attempt and evidence; go to ready only if the correction is known and permitted, otherwise blocked or planned. Apply the retry conditions in Efficient tool execution; a known correction alone is not evidence that the input changed. Never reuse an attempt ID for a retry. Ordinary lifecycle bookkeeping follows existing scope authorization; it does not approve design changes.

## Accept a result

Require the Worker contract's result fields. A tool reporting completion or a worker saying PASS is not acceptance.

1. Match task, active attempt and authority revision. Preserve unmatched or superseded returns as stale evidence; do not merge or mark done automatically.
2. Inspect the actual current deliverable or result and confirm the returned baseline/diff, scope, prerequisites and required checks. For research, distinguish primary facts, inferences and unknowns. For implementation, inspect the frozen candidate's actual diff and validation. For review, require separate Design and Standards conclusions. A first delivery needs evidence for the complete approved acceptance scope; for a revision, identify the exact changes, invalidated conclusions and still-valid evidence before repeating verification. Keep this explanation in the existing record or return, not a new form. For an unresolved automated-check selection or reuse question, use the shared [testing method](../../ddd-implement/references/testing.md), reusing already applicable guidance.
3. Compare each acceptance criterion with relevant actual content or behavior and its source or independently justified expectation. Verify the evidence's identity, coverage and validity, then resolve remaining questions rather than repeating the worker's entire investigation. A small diff can change substantial meaning: check the affected complete semantic unit and its dependencies; a shared method, dependency or interface change extends review to exposed results. Retain still-required final integration, integrity and delivery checks. Inventories, counts, hashes and links establish their own properties, not semantic conformity. Report the checked scope without presenting unchecked content or behavior as verified or replacing complete coverage with unapproved sampling. For source-backed document conversion or restructuring, use [source conversion review](../../chinese-docs/references/review.md#source-conversion-review), retrieving the method only if missing. If authority changed, assess affected output against the new contract; return material design choices to the user through ddd-flow. Do not edit design to accept a result.
4. Record accepted evidence and next work. Only the main conversation marks done. A missing required check remains incomplete; preserve failures, do not hide them behind unrelated passing checks. If later evidence contradicts an accepted result, identify which transformation, dependency or acceptance claim is implicated and reopen verification of the affected results or claims. Check earlier results exposed to the same defect within authorization; retain prior attempts, failures, authentic user decisions and independent valid evidence. Do not reject or recheck unrelated results, and leave unresolved technical claims unaccepted while independent authorized work continues.

Apply [Evidence validity](#evidence-validity), reusing its valid excerpt. Design and Standards are two review axes, not a requirement for two workers.

## Resume from durable evidence

Use [project recovery](recovery.md) for the general summary, authority and next-action sequence and its record-maintenance rules; this section adds only managed-attempt recovery. Reuse that completed recovery rather than reading the same sources again.

Check the old worker through host status when its handle is usable. A persisted running status is not proof it is alive or dead. If liveness is unknown, block overlapping writes and investigate; continue independent tasks. If it is confirmed stopped, inspect partial changes before making a new attempt. Never redispatch solely because context changed.

Match returned results to their recorded task, active attempt and actual candidate before accepting them. Reuse valid accepted results through Accept a result without repeating completed work. Reject stale attempts and identify the earliest ready task; report unresolved evidence or liveness explicitly. If attempt evidence is missing, recover only those facts from available sources and retain the gap; do not restart general recovery or invent a previous decision.

Memory and handoff point to this record and the authority owners; they do not maintain another task state. Resume does not automatically create a new user-visible conversation or authorize any previously uncovered action.
