# Project recovery and handover

Read these steps across a context boundary or when the active pointer or record is missing or stale. Compare relevant records with the verified installed specification using [project adaptation](project-adaptation.md); reuse unchanged facts and repair deterministic structural gaps only within authorized writes. Read the later section for an expensive fact or explicit portable handover. This is a lookup path, not another state store. Managed attempts also use the needed [execution recovery](execution.md#resume-from-durable-evidence) sections.

1. Confirm the specified project root, sub-workspace, effective instructions and actual Git state, including staged, unstaged and untracked changes. Never infer a clean or approved state from an old summary.
2. Read `.planning/STATE.md` only to locate the explicitly requested change or the unique observed binding for this conversation, then that `record.md` summary. Unknown or multiple matching owners require resolving selection; never take over the newest record. Schema 1 retains its single-pointer lookup, with no invented conversation ownership. Read the relevant `.planning/PROJECT.md` clauses and approved requirements, design, prototype or slice objects for the requested action. Do not scan every historical change or repeat onboarding.
3. Check the recorded approval objects against recoverable content identities and current files. A changed hash needs semantic comparison, not automatic cancellation or automatic acceptance. Reuse checks only while their code, inputs and environment remain relevant.
4. Determine the current `phase` and `status`, the last accepted result, real blockers, technical verdict, user acceptance, and one next action inside existing permission. A task can be technically complete while awaiting user acceptance; do not set acceptance from a test result.
5. Reconstruct missing pointers or records only from observable files, Git and authentic user evidence. Preserve unknown approval as unknown. Authorized task record maintenance covers necessary restoration and lossless structural migration; read-only or explicitly excluded writes report the gap. Never fabricate consent or overwrite user changes to fit a template.

Update the record only for actual approval or withdrawal, baseline change, slice result, blocker, acceptance, handover or a necessary structural migration. `STATE.md` remains a conversation index; each record owns its own status and evidence. Keep the current summary consistent with the latest effective approval, withdrawn constraints and next action; retain superseded decisions with their sources in history, without reviving them during recovery. Link existing task and design owners; do not duplicate history or bulk-migrate unrelated records. Use the [record template](../assets/record.md) for the current task's necessary structure.

## State vocabulary

Read or reuse this bounded section before changing phase/status fields, including prototype-only record updates; it does not require reading the full recovery method. `phase` is `requirements`, `design`, `planning`, `implementation`, `verification`, `acceptance` or `closed`; `status` is `working`, `awaiting_user`, `blocked`, `done` or `cancelled`. A technically complete approved outcome awaiting G4 uses `phase: acceptance`, `status: awaiting_user`, `technical_verdict: PASS`, `user_acceptance: pending`. A partial check does not advance a whole unfinished change to acceptance; an unapproved design still waits at its actual gate. Do not invent labels such as `awaiting_acceptance` or use `implementation` to describe a finished outcome awaiting G4.

After authorized record writes, inspect its actual fields and use the existing [workflow checker](../scripts/workflow_check.py) for the selected change when certifying its structural validity. This read-only record check belongs to the authorized record maintenance, not a new product test or an approval check. Repair unsupported states within existing scope before claiming the record is valid; preserve actual approvals and unknowns. Migrate an old state only when its meaning maps unambiguously; an uncertain mapping returns to its owner without resetting acceptance.

## Recover facts without a second memory store

Find the owner of each fact before saving a recovery note. Requirements, design, CONTEXT and ADRs own intended behavior and durable approved decisions; the current record owns execution state; reports own research and check evidence; Git and code show the current implementation. Distinguish approved decisions, observed facts, stale summaries and inferences. Verify mutable facts before reuse. Save only expensive-to-recover facts or an otherwise missing return point, with concise evidence pointers and no secrets or copied logs. If an existing `.codex/memory/` store may contain a relevant fact, read its `INDEX.md` and then only the relevant entry files; verify their claims against current authority and implementation. Do not initialize a new store by default, rewrite its history, or treat a stored claim as approval. Do not read or maintain the host's private native memory directory.

Map legacy requests to their current owner: `init` means authorized project adoption; `recall` means the bounded recovery path above; `checkpoint` means updating the active record when authorized and materially changed; `decide` means placing an approved decision in its design, ADR or record owner; `audit` means checking evidence validity; `compact` means a concise context handover at a real boundary. These are intents, not six mandatory commands or permission to write. Existing legacy stores remain intact until separately authorized migration or removal.

For an explicitly requested portable handover, give the next context the current objective, still-valid permissions, authority and record pointers, uncommitted state, active operation handles or unresolved liveness, blockers and the exact next action. Link existing design, task, report and Git evidence instead of copying it. Return a copyable handover in the conversation unless persistence is authorized; use the requested project location only when that artifact is approved. A healthy continuing context does not need a handover or a new user-visible conversation.
