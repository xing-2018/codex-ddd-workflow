# Project recovery and handover

This reference owns general project recovery. Use these steps only for information missing or stale after a context boundary or in the active binding. Reuse available authority and evidence; recover the current record and needed source portions instead of reloading the workflow package. Use [project adaptation](project-adaptation.md) for an unresolved specification difference and repair deterministic structural gaps only within authorized writes. The later section covers expensive fact recovery or an explicit portable handover; [execution recovery](execution.md#resume-from-durable-evidence) adds only missing managed-attempt facts. This lookup creates no second state store.

For background from another conversation, apply [Conversation evidence](execution.md#conversation-evidence) before requesting history. A recovery pointer does not mean already available instructions need a full reload; identify missing authority and guidance first. An explicit refresh or known update still follows the router's conditional loading rule.

1. Confirm the specified project root and sub-workspace. Follow an already known unique conversation binding or valid recovery pointer to the current `record.md` summary; consult `.planning/STATE.md` only when that binding is missing, stale or conflicting. Resolve unknown or multiple bindings; never select the newest record or scan history. Schema 1 keeps its single-pointer lookup without invented ownership. Optional adapters and the shared manual helper are described in [lifecycle adapters](lifecycle-hooks.md); no hook output grants approval.
2. Recover the current goal and scope, effective approval and withdrawals, accepted results and evidence boundaries, real blockers, active operation handles and one next action. Determine actual `phase`, `status`, technical verdict and user acceptance without equating them. A task can be technically complete while awaiting user acceptance; a test result cannot set it. Read history or linked owners only for a specific missing fact or contradiction.
3. Check the effective instructions and actual Git state, including staged, unstaged and untracked changes, and the current inputs, dependencies or runtime state relevant to that next action. Never infer a clean or approved state from an old summary. Compare recorded approval objects with recoverable identities and current relevant content; a changed hash needs semantic comparison, not automatic cancellation or acceptance. A stored hash alone proves neither approval nor valid check scope.
4. Retrieve only the missing, changed or conflicting authority clauses and method sections needed for the next action, including an explicitly requested or known applicable refresh. A record saying "loaded" does not prove the text is still available; recover the genuinely missing section. Compaction or a phase transition alone does not require rereading whole Skills, project documents or unchanged identities. Reuse valid evidence and continue the ready action; obtain managed-attempt facts only when still unresolved.
5. Reconstruct missing pointers or records only from observable files, Git and authentic user evidence. Preserve unknown approval as unknown. Authorized task record maintenance covers necessary restoration and lossless structural migration; read-only or explicitly excluded writes report the gap. Never fabricate consent or overwrite user changes to fit a template.

Update the authorized record only for actual approval or withdrawal, baseline change, slice result, blocker, acceptance, handover or a necessary structural migration. `STATE.md` remains a conversation index; each record owns its own status and evidence. Keep its current summary consistent with the goal, latest effective approval and withdrawals, baseline, accepted evidence and applicability, active operation handles, blockers and next action. Retain verified command entry points, working directory and applicability only when costly to recover and useful next, or point to their existing owner; do not register every command or maintain a loaded-file inventory. Link older attempts, task/design owners and full evidence rather than copying them; retain superseded decisions without reviving them during recovery. Existing records need only relevant maintenance, not bulk migration. Use the [record template](../assets/record.md) for necessary structure; create no second tracker or secret store.

## State vocabulary

Read or reuse this bounded section before writing DDD record fields, bindings or body, including initialization, prototype-only updates and evidence or command notes; it does not require reading the full recovery method. `phase` is `requirements`, `design`, `planning`, `implementation`, `verification`, `acceptance` or `closed`; `status` is `working`, `awaiting_user`, `blocked`, `done` or `cancelled`. A technically complete approved outcome awaiting G4 uses `phase: acceptance`, `status: awaiting_user`, `technical_verdict: PASS`, `user_acceptance: pending`. A partial check does not advance a whole unfinished change to acceptance; an unapproved design still waits at its actual gate. Do not invent labels such as `awaiting_acceptance` or use `implementation` to describe a finished outcome awaiting G4.

Finish authorized record content before its final structural check. Reuse identifiable evidence only for the actual covered inputs, or run [workflow_check.py](../scripts/workflow_check.py) for the selected change, including the observed thread when claiming schema-2 ownership under [Conversation index](project-adaptation.md#conversation-index). Checker inputs include record prose, evidence notes and command examples, not only phase/status: whole-text placeholder and safe-path checks can change when that body changes. After a check, compare any later write with its checked scope and recheck affected final record inputs; unchanged status fields alone do not preserve the result. Do not add command placeholders after checking and call the previous result final.

Keep the final receipt in an already authorized evidence location outside the checked records when possible. If writing a result back changes a checked record, assess and recheck that change, then retain the final receipt without another unassessed writeback loop. Apply [Evidence validity](execution.md#evidence-validity): metadata-only changes reopen affected structure, not unchanged product behavior tests. Retain original failed outputs, complete authorized deterministic field/path/placeholder repairs and report the actual checker status; `NEEDS_REVIEW` is a remaining record gap, not structural `PASS`. Enabled record adapters call the same checker; silence does not prove a hook ran. This is record maintenance, not a product test or approval check. Uncertain semantic mappings return to their owner without resetting acceptance. [Adapter coverage and fallback](lifecycle-hooks.md#record-checking) do not change this policy.

## Recover facts without a second memory store

Find the owner of each fact before saving a recovery note. Requirements, design, CONTEXT and ADRs own intended behavior and durable approved decisions; the current record owns execution state; reports own research and check evidence; Git and code show the current implementation. Distinguish approved decisions, observed facts, stale summaries and inferences. Verify mutable facts before reuse. Save only expensive-to-recover facts or an otherwise missing return point, with concise evidence pointers and no secrets or copied logs. If an existing `.codex/memory/` store may contain a relevant fact, read its `INDEX.md` and then only the relevant entry files; verify their claims against current authority and implementation. Do not initialize a new store by default, rewrite its history, or treat a stored claim as approval. Do not read or maintain the host's private native memory directory.

Map legacy requests to their current owner: `init` means authorized project adoption; `recall` means the bounded recovery path above; `checkpoint` means updating the active record when authorized and materially changed; `decide` means placing an approved decision in its design, ADR or record owner; `audit` means checking evidence validity; `compact` means a concise context handover at a real boundary. These are intents, not six mandatory commands or permission to write. Existing legacy stores remain intact until separately authorized migration or removal.

For an explicitly requested portable handover, give the next context the current objective, still-valid permissions, authority and record pointers, uncommitted state, active operation handles or unresolved liveness, blockers and the exact next action. Link existing design, task, report and Git evidence instead of copying it. Return a copyable handover in the conversation unless persistence is authorized; use the requested project location only when that artifact is approved. A healthy continuing context does not need a handover or a new user-visible conversation.
