# Review：代码审阅

> 仅供人工阅读的中文译本，对应同目录[SKILL.md](SKILL.md)。本文件不是Skill加载入口；执行规则以原文为准。仅翻译入口正文及用途说明，引用文件保留原文。

用途：针对冻结的代码差异或明确代码路径快照，审查设计或规范一致性及工程质量；可用于实现后审阅，也可独立审查代码、复杂性或范围蔓延。

对冻结范围分别进行**Design（已批准行为）**与**Standards（工程质量）**审阅。一个轴通过不能抵消另一个轴失败。默认只读；修复需要明确请求或外围实现任务的授权。

涉及产品变化、版本或交付时，适用[版本与交付](../ddd-flow/references/versioning-and-delivery.md)，只读取尚未解决的指导，复用有效项目配置和判断。明确可丢弃且不改变产品或交付物的夹具没有版本与交付工作。针对冻结范围评估兼容性、已确认基线、适用版本与交付物配置及证据。仅源码交付的部分检查可以保留为待完成；独立审阅既不升版，也不构建。相关发现仍归入既有两个轴。

## 1. 冻结审阅范围

变更审阅须核对比较起点，记录差异命令、变更文件和提交清单。独立审阅须记录指定修订下的明确路径，或当前内容哈希；不编造差异。没有固定范围时，两个轴均为`BLOCKED`。将与所审行为相关但未修改的测试也纳入同一修订或已记录哈希的核对范围；遵守明确限定的读取范围，并报告因此缺少的测试证据。

使用已有的适用AGENTS、领域上下文和已批准设计；只补读缺失或失效的权威依据，包括相关专项和上游权威。UI变化还须将已批准的原型版本及适用本地资源纳入冻结的设计基线；未经批准的截图不能替代设计。当前用户要求、会话批准和路由器的权威基线都是有效依据；即便没有设计文件，也引用可恢复的决策。任务、配置、代码和通过的测试是证据，不是批准。缺少实质性权威时，Design为`NOT_ASSESSABLE`；已批准条款冲突时为`BLOCKED`。两种情况下均继续Standards审阅。不得改写设计或降低验收标准来使偏离合理化。

小型审阅留在本地并复用既有职责判断。独立的实质性有界审阅缺少判断时，仅提取[ddd-flow的Choose execution ownership](../ddd-flow/SKILL.md#choose-execution-ownership)，不遍历完整流程。独立审阅有依据且被允许时，随本方法派发有界Worker contract摘录。worker只用本方法与契约，不加载派发、状态、验收和恢复章节，在依赖工作前补齐缺失摘录，保持只读，不委派或重复管理判断，返回发现供主会话验收。主会话核实证据并协调授权修复。复用PASS前重新核实已被替代的差异或设计证据；除非共享变化使更大范围证据失效，否则只重复受影响检查。同一worker可审阅两个轴。

## 2. Design轴

将每项适用需求追溯到固定实现及验证证据。变更审阅聚焦差异，快照审阅评估选定路径。检查：

- 行为缺失、实现不完整或语义错误；
- 算法、公式、单位、阈值、数据、接口、状态、顺序、时序和失败行为；
- 配置、持久化、并发、部署和安全偏离；
- 未请求的行为、回退、兼容路径、扩展点，以及明确排除项；
- 实现与测试是否共享同一个错误假设。

引用权威与实现，将需求分类为`PASS`、`PARTIAL`、`MISSING`、`WRONG`或`NOT_ASSESSABLE`。仅Standards请求可能没有适用的设计需求。分别报告技术验证与适用的G4用户验收；测试或双轴审阅通过不能将`user_acceptance`记为已接受。需要用户验收时，提供实际版本、入口、已实现范围和简短检查路径。

UI变化须在相同场景、数据、交互状态和产品窗口尺寸下，比较最新批准入口及依赖资产与已实现目标页面和受影响的共享使用方。包含保留的导航／选择／草稿状态、默认值及禁用与隐藏的区别。视觉和可操作路径的结论须有对应的实际证据；构建、DOM结构或算法测试不能替代。缺少证据须保留为可追踪缺口，不得笼统判PASS。声称时间或原生行为时，须有相应证据。不要向受限原型包添加截图，也不从技术审阅推断用户验收。

比较时应用[ddd-design的布局稳定与任务内容默认规则](../ddd-design/references/ui-design.md#stable-layout-and-task-focused-content)，复用已加载的有效指导。检查受影响的空、加载、禁用和失败状态中，不必要的解释内容与布局变化，以及有用且可访问的反馈。具体批准的例外仍具权威；此引用不增加设计门槛或写入权限。

对于完成或性能声明，检查批准指标与实际边界：请求超时不是总处理目标，数值自洽检查不等于物理验证，开发模式不等于打包入口。纠正后只重评受影响证据，除非共享契约变化使更广范围的证据失效；保留独立有效的检查和历史失败证据。

## 3. Standards轴

实质代码质量判断共用[代码规范入口](../ddd-implement/references/code-style.md)及适用语言章节，项目规范优先；不复制规则或扩大为工具／配置迁移。

优先遵循仓库标准。以下代码异味作为判断线索，不自动判为违规：

| 异味 | 检查问题 |
| --- | --- |
| 命名费解（Mysterious Name） | 名称能否揭示含义？ |
| 重复代码（Duplicated Code） | 相同逻辑是否重复？ |
| 依恋其他模块（Feature Envy） | 行为是否更依赖另一模块的数据？ |
| 数据泥团（Data Clumps） | 一组字段是否反复一起传递？ |
| 基本类型偏执（Primitive Obsession） | 基本类型是否掩盖了领域概念？ |
| 重复分支（Repeated Switches） | 相同的按类型分支是否反复出现？ |
| 散弹式修改（Shotgun Surgery） | 一项变化是否散布到多个模块？ |
| 发散式变化（Divergent Change） | 一个模块是否因互不相关的原因而变化？ |
| 猜测性通用化（Speculative Generality） | 现在是否需要这个变化点？ |
| 消息链（Message Chains） | 调用者是否必须了解很长的对象访问路径？ |
| 中间人（Middle Man） | 转发是否封装了有意义的复杂性？ |
| 拒绝继承契约（Refused Bequest） | 继承是否遵守继承来的契约？ |

每个新增文件、类型、抽象、接口、适配器、依赖、配置、兼容路径和失败分支都须有当前理由。真实模块深度、接口、接缝或局部性问题才读取[架构方法](../ddd-design/references/architecture.md)。遇测试选择或维护问题使用[测试与测试维护](../ddd-implement/references/testing.md)，不调用TDD。核查检查覆盖变化声明、复用有效结果、扩大／复跑有具体理由，并在原结果及必需保护确立后停止。审查永久新增和有界精简：确认低价值的范围内用例须处理，删除后保留不同的行为、失败路径和边界。保留不确定／范围外保护的缺口；覆盖相同或数量少不足以删除。明确违规归Standards，不降为可选清理。复用有效架构／测试证据，不因审阅或阶段变化再跑套件。

候选用于本地提交、交接或推送时，对拟定或已暂存边界，或准确范围中的每个提交，应用共用[Git组织与说明检查](../ddd-flow/references/git.md#commit-organization)。结合目的、必要依赖、完整差异和说明判断。确认的违规归Standards发现；技术检查通过或传入的PASS字段不能代替该判断。缺少评估边界所必需的证据时，阻塞Standards的这部分判断，继续独立Design审阅。质量发现不授权改写历史或其他Git操作。

## 4. 分别报告两个轴

先报告Design发现与需求追溯，再报告Standards发现，随后分别给出结论：

- Design：`PASS`、`FAIL`、`BLOCKED`或`NOT_ASSESSABLE`。
- Standards：`PASS`、`FAIL`或`BLOCKED`。

每项发现引用证据，说明实际影响和最小修正方向。不合并评分，不掩盖无法评估的Design轴。委派审阅按提供的Worker contract摘录返回字段，并包含两个结论；主会话验收当前证据。
